개발자는 보통 다음과 같은 코드를 작성한다.

```c
#include <stdio.h>

int main() {
    int a = 3;
    int b = 5;
    int c = a + b;

    printf("%d\n", c);

    return 0;
}
```

코드를 실행하면 화면에는 간단히 `8`이 출력된다.

하지만 컴퓨터 입장에서 우리가 작성한 C 코드는 그냥 **텍스트 파일**이다.

CPU는

```c
int c = a + b;
```

라는 문장을 이해하지 못한다.

결국 프로그램을 실행하려면 사람이 이해하기 쉬운 소스코드를 CPU가 이해할 수 있는 기계어로 바꾸는 과정이 필요하다.

이번 글에서는 가장 먼저 **소스코드가 실행파일이 되는 과정**부터 살펴본다.

---

## 1. 실행파일도 실행 전에는 그냥 데이터다

먼저 C 프로그램을 컴파일해보자.

```bash
gcc add.c -o add
```

그러면 Linux 기준으로 `add`라는 실행파일이 만들어진다.

여기서 중요한 점이 있다.

> 디스크에 저장되어 있는 실행파일은 아직 실행 중인 프로그램이 아니다.

실행파일 내부에는 CPU가 이해할 수 있는 기계어 명령어가 들어 있지만, 디스크에 저장되어 있는 동안에는 그저 바이트 데이터일 뿐이다.

CPU가 실행파일 안의 명령어를 계속 읽고 있는 것도 아니다.

프로그램을 실제로 실행해야 운영체제가 실행파일을 메모리로 가져오고 CPU가 명령어를 처리하기 시작한다.

전체 흐름을 먼저 보면 다음과 같다.

```text
소스코드
  ↓
컴파일
  ↓
실행파일
  ↓
디스크에 저장
  ↓
실행
  ↓
RAM에 로드
  ↓
CPU가 명령어 실행
  ↓
프로그램 종료
```

그렇다면 C 소스코드는 어떤 과정을 거쳐 실행파일이 되는 것일까?

---

## 2. C 컴파일은 실제로 4단계를 거친다

우리는 보통 다음 한 줄로 컴파일한다.

```bash
gcc add.c -o add
```

하지만 내부적으로는 크게 다음 네 과정이 수행된다.

```text
전처리
→ 컴파일
→ 어셈블
→ 링킹
```

결과물까지 포함하면 다음과 같다.

```text
add.c
 ↓ 전처리
add.i
 ↓ 컴파일
add.s
 ↓ 어셈블
add.o
 ↓ 링킹
add
```

---

## 3. 1단계 — 전처리 Preprocessing

첫 단계는 전처리다.

```bash
gcc -E add.c -o add.i
```

전처리기는 다음과 같은 지시문을 처리한다.

```c
#include
#define
```

예를 들어

```c
#include <stdio.h>
```

가 있으면 `stdio.h`의 내용을 반영한다.

결과는 `.i` 파일이다.

```text
add.c
 ↓
add.i
```

이 시점의 파일은 아직 사람이 읽을 수 있는 C 코드다.

---

## 4. 2단계 — 컴파일 Compilation

다음으로 전처리된 C 코드를 어셈블리 코드로 변환한다.

```bash
gcc -S add.i -o add.s
```

예를 들어

```c
int c = a + b;
```

라는 코드가 있다면 어셈블리에서는 대략 다음과 같은 형태로 표현된다.

```asm
mov eax, [a]
add eax, [b]
mov [c], eax
```

이 단계에서는 문법 오류 확인과 최적화도 이루어진다.

결과는

```text
add.s
```

라는 어셈블리 텍스트 파일이다.

---

## 5. 3단계 — 어셈블 Assembly

다음은 어셈블리 코드를 기계어로 바꾸는 단계다.

```bash
gcc -c add.s -o add.o
```

결과는

```text
add.o
```

라는 Object File이다.

이 파일은 이미 기계어를 포함하고 있다.

하지만 아직 완전한 실행파일은 아니다.

예를 들어 코드에서 사용한

```c
printf()
```

가 실제로 어디에 있는지 최종적으로 연결되지 않았기 때문이다.

즉 Object File에는 외부 함수에 대한 심볼 정보 등이 남아 있다.

---

## 6. 4단계 — 링킹 Linking

마지막 단계가 링킹이다.

```bash
gcc add.o -o add
```

링커는 Object File과 필요한 라이브러리를 연결한다.

```text
add.o
+
Library
+
다른 Object File
        ↓
최종 실행파일
```

이 단계가 끝나면 CPU가 실행할 수 있는 최종 실행파일이 만들어진다.

---

## 7. 전체 과정 다시 보기

정리하면 다음과 같다.

```text
C Source

add.c
 ↓
Preprocessing

add.i
 ↓
Compilation

add.s
 ↓
Assembly

add.o
 ↓
Linking

add
```

여기까지가 **프로그램 실행 이전**에 일어나는 일이다.

이후 우리가

```bash
./add
```

를 입력해야 운영체제가 개입하면서 실제 실행 과정이 시작된다.

---

## 8. 그렇다면 Python은?

Python은 C와 실행 방식이 다르다.

다음 코드를 생각해보자.

```python
a = 3
b = 5
c = a + b

print(c)
```

Python은 C처럼 프로그램 실행 전에 전체 코드를 최종 기계어 실행파일로 만들어두는 방식으로 설명되지 않는다.

실행 흐름은 문서에서 다음과 같이 정리된다.

```text
Python Source
     ↓
소스코드 읽기
     ↓
Parsing
     ↓
AST
     ↓
Bytecode
     ↓
Python Virtual Machine
     ↓
실행
```

Python 역시 내부적으로 소스코드를 바로 한 줄씩 CPU에 전달하는 것이 아니라 **Bytecode라는 중간 형태**를 사용한다.

---

## 9. C와 Python의 핵심 차이

문서의 설명을 간단하게 정리하면 다음과 같다.

| 구분         | C        | Python             |
| ---------- | -------- | ------------------ |
| 번역 시점      | 실행 전     | 실행 과정              |
| 중간/최종 결과   | 기계어 실행파일 | Bytecode           |
| 실행 시 필요한 것 | 실행파일     | Python Interpreter |
| 실제 계산      | CPU      | PVM을 거쳐 CPU        |

C는

```text
Source
→ Machine Code
→ CPU
```

에 가깝고,

Python은

```text
Source
→ Bytecode
→ PVM
→ CPU
```

라는 한 단계가 더 존재한다.

## 마무리

이번 글에서는 소스코드가 실행되기 이전 단계까지 살펴봤다.

핵심 흐름은 다음과 같다.

```text
사람이 작성한 코드
      ↓
Compiler
      ↓
Assembly
      ↓
Machine Code
      ↓
Executable
```

하지만 아직 중요한 질문이 하나 남아 있다.

> 실행파일을 더블클릭하거나 `./add`를 입력하는 순간 실제로 무슨 일이 일어날까?

다음 글에서는 **운영체제, 프로세스, 메모리** 관점에서 실행파일이 실제 프로그램으로 바뀌는 과정을 살펴본다.
