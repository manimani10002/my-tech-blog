# 서비스를 만들기 위한 기술 스택 선정 (1) — Frontend, Backend, Database

> 하나의 서비스를 만들기 위해 어떤 기술이 필요하고, 무엇을 기준으로 선택해야 할까?

지난 글에서는 Product Engineer라는 직무를 알아보고, 풀스택 개발 역량을 갖추기 위해 작은 서비스를 E2E(End-to-End)로 개발해보기로 했다.

본격적으로 개발하기 전에 기술 스택을 선정하는 과정에서 한 가지 의문이 생겼다.

지금까지 팀 프로젝트를 진행하면서 React, Vue, TypeScript 등 여러 기술을 사용해왔다. 하지만 기술을 선택할 때는 주로 기존에 사용해봤거나 팀원들이 익숙한 기술을 선택했다.

물론 익숙한 기술을 선택하는 것도 합리적인 기준이다.

하지만 **각 기술의 특징과 어떤 상황에 적합한지를 설명하지 못한 채 관성적으로 사용하는 것**은 좋은 선택이 아니라고 생각한다.

그래서 이번 프로젝트에서는 기술 스택을 선정하면서 다음 세 가지를 함께 학습하기로 했다.

- 각 기술은 서비스에서 어떤 역할을 하는가?
- 같은 역할을 하는 기술에는 어떤 것들이 있는가?
- 프로젝트의 목적과 요구사항에 따라 어떤 기술을 선택해야 하는가?

이번 글에서는 그중 Frontend, Backend, Database에 대해 정리해보려고 한다.

---

## 1. 기술 스택을 선정하기 전에

기술 스택(Tech Stack)은 서비스를 개발하고 운영하기 위해 사용하는 기술의 조합을 의미한다.

프로그래밍 언어, 라이브러리, 프레임워크뿐 아니라 데이터베이스, 서버, 배포 도구 등도 포함된다.

이번 Todo List 프로젝트의 기술 스택은 다음과 같다.

| 영역 | 기술 |
| :--- | :--- |
| Frontend | React, TypeScript, Vite |
| Backend | Java 21, Spring Boot |
| Database | PostgreSQL |
| Container | Docker, Docker Compose |
| Web Server | Nginx |
| Server | Ubuntu VM |
| CI/CD | GitHub Actions |

Todo List라는 서비스의 기능만 생각하면 다소 많은 기술을 사용한다고 느낄 수 있다.

실제로 간단한 Todo List라면 백엔드 없이 브라우저의 LocalStorage를 사용해 구현할 수도 있고, Firebase나 Supabase를 활용하면 서버와 데이터베이스를 직접 구축하지 않아도 된다.

하지만 이번 프로젝트의 목적은 빠르게 서비스를 만드는 것이 아니다.

**서비스가 개발되고 배포되는 전체 과정을 직접 경험하는 것이 목적이다.**

따라서 기술을 선택할 때도 개발 속도뿐 아니라 해당 기술을 통해 무엇을 학습할 수 있는지를 고려했다.

기술 스택을 선정하기 위해서는 **먼저 프로젝트의 목적을 명확히 해야 한다는 것**을 알게 되었다.

## 2. 하나의 서비스를 구성하는 기술 영역

각 기술을 알아보기 전에 서비스의 전체 구조부터 살펴보자.

이번 프로젝트에서 계획한 아키텍처를 단순화하면 다음과 같다.

![할 일 목록 구조](/images/todo-list-structure.svg)

React의 빌드 결과물은 Nginx가 제공하고, 브라우저에서 발생한 API 요청은 Nginx를 거쳐 Spring Boot로 전달하는 구조를 계획하고 있다.

Spring Boot는 PostgreSQL에 접근해 데이터를 저장하거나 조회한다.

각 기술 영역의 역할을 간단하게 정리하면 다음과 같다.

| 영역 | 역할 |
| :--- | :--- |
| Frontend | 사용자가 보는 화면과 상호작용 구현 |
| Backend | 요청 처리 및 비즈니스 로직 실행 |
| Database | 데이터 저장 및 관리 |
| Container | 애플리케이션 실행 환경의 격리와 재현 |
| Web Server | HTTP 요청 처리, 정적 파일 제공, 요청 전달 |
| Server | 애플리케이션이 실행되는 환경 제공 |
| CI/CD | 코드 검증, 빌드, 배포 과정 자동화 |

모든 서비스가 반드시 이 일곱 가지 영역을 별도로 구성해야 하는 것은 아니다. 관리형 플랫폼을 사용하면 일부 영역을 직접 구축하지 않아도 된다.

이번 글에서는 실제 서비스의 기능을 구현하는 Frontend, Backend, Database를 먼저 알아보자.

## 3. Frontend — 사용자와 서비스의 접점

### Frontend란 무엇인가?

프론트엔드는 사용자가 직접 보고 상호작용하는 영역이다.

Todo List를 예로 들면 다음과 같은 기능이 해당한다.

- 할 일 목록을 화면에 표시한다.
- 입력창에서 사용자의 입력을 받는다.
- 완료 버튼을 누르면 화면을 갱신한다.
- 백엔드에 데이터를 요청하고 응답을 처리한다.
- 요청이 실패하면 오류 메시지를 표시한다.

웹 프론트엔드의 기본 기술은 HTML, CSS, JavaScript다.

| 기술 | 역할 |
| :--- | :--- |
| HTML | 웹 페이지의 구조 |
| CSS | 웹 페이지의 스타일과 레이아웃 |
| JavaScript | 사용자 이벤트 처리와 동적인 동작 |

이 세 가지 기술만으로도 웹 서비스를 만들 수 있다.

그렇다면 React나 Vue 같은 기술은 왜 사용하는 것일까?

### UI 라이브러리와 프레임워크

서비스가 복잡해지면 관리해야 하는 데이터와 화면의 상태도 많아진다.

예를 들어 Todo List에 다음과 같은 기능이 추가된다고 가정해보자.

- 할 일 추가, 수정, 삭제
- 완료 여부에 따른 필터링
- 남은 할 일 개수 표시
- 서버 요청에 따른 로딩 및 오류 처리

JavaScript만으로 구현할 경우 데이터가 변경될 때 어떤 DOM 요소를 어떻게 변경할지 직접 관리해야 한다.

React나 Vue를 사용하면 화면을 컴포넌트 단위로 나누고, 데이터의 상태에 따라 화면을 갱신하는 방식으로 개발할 수 있다.

```text
사용자 이벤트
      ↓
데이터 및 상태 변경
      ↓
UI 갱신
```

이러한 기술은 복잡한 UI를 관리하고, 코드를 재사용하며, 유지보수하기 쉽게 만드는 데 도움을 준다.

대표적인 기술로 React, Vue, Angular, Svelte, Next.js가 있다.

| 기술 | 분류 | 특징 |
| :--- | :--- | :--- |
| React | UI 라이브러리 | 컴포넌트 기반 개발, 유연한 구조 |
| Vue | 프레임워크 | 점진적인 도입, 선언적인 UI 구현 |
| Angular | 프레임워크 | 체계적인 구조와 다양한 내장 기능 |
| Svelte | 컴파일러 기반 UI 프레임워크 | 컴파일 단계에서 UI 코드 변환 |
| Next.js | React 기반 웹 프레임워크(풀스택) | 파일 기반 라우팅, 서버 사이드 렌더링 및 정적 페이지 생성 지원 |

라이브러리와 프레임워크의 차이도 알아둘 필요가 있다.

일반적으로 라이브러리는 개발자가 필요한 기능을 선택해서 사용하는 도구에 가깝고, 프레임워크는 애플리케이션을 개발하는 전체적인 구조와 규칙을 제공한다.

React는 UI 구현에 집중하기 때문에 라우팅이나 상태 관리 등의 기술을 프로젝트에 맞게 선택할 수 있다.

반면 Angular는 라우팅, 폼 처리, 의존성 주입 등 애플리케이션 개발에 필요한 다양한 기능과 구조를 제공한다.

다만 라이브러리와 프레임워크의 경계가 항상 명확한 것은 아니다.

### 어떤 기술을 선택해야 할까?

각 기술의 특징을 바탕으로 선택 기준을 정리해봤다.

| 기술 | 선택을 고려할 상황 | 고려할 점 |
| :--- | :--- | :--- |
| React | 풍부한 생태계와 유연한 기술 구성이 필요한 경우 | 추가 라이브러리 선정과 아키텍처 설계가 필요할 수 있음 |
| Vue | 점진적인 도입과 비교적 쉬운 학습이 중요한 경우 | 팀의 경험과 필요한 생태계 확인 |
| Angular | 여러 개발자가 일관된 구조와 규칙을 유지해야 하는 경우 | 프레임워크의 개념과 규칙에 대한 학습 비용 |
| Svelte | 간결한 코드와 컴파일러 기반 접근 방식을 원하는 경우 | 필요한 라이브러리와 팀의 숙련도 확인 |

React가 모든 서비스에 적합하거나 Angular가 반드시 대규모 서비스에만 적합한 것은 아니다.

서비스의 복잡도, 팀원의 기술 역량, 필요한 라이브러리, 유지보수 방식 등을 종합적으로 고려해야 한다.

### CSR과 SSR

프론트엔드 기술을 선택할 때는 화면을 어디에서 렌더링하는지도 고려해야 한다.

대표적인 렌더링 방식은 CSR과 SSR이다.

**CSR(Client-Side Rendering)**

브라우저에서 JavaScript를 실행해 화면을 구성하는 방식이다.

```text
Browser
   ↓ 페이지 요청
Web Server
   ↓ HTML / CSS / JavaScript 전달
Browser
   ↓ JavaScript 실행
화면 렌더링
```

사용자와의 상호작용이 많은 웹 애플리케이션에서 활용할 수 있다.

다만 초기 JavaScript 로딩과 실행 비용이 크면 첫 화면이 표시되는 시간이 길어질 수 있다.

**SSR(Server-Side Rendering)**

서버에서 HTML을 생성한 뒤 브라우저에 전달하는 방식이다.

```text
Browser
   ↓ 페이지 요청
Server
   ↓ HTML 생성
Browser
   ↓ HTML 표시
화면 렌더링
```

초기 콘텐츠 제공이나 검색 엔진 최적화(SEO)가 중요한 서비스에서 고려할 수 있다.

대신 서버에서 렌더링을 수행하기 때문에 서버 운영과 캐싱 전략 등 추가적인 고려사항이 생긴다.

| 구분 | CSR | SSR |
| :--- | :--- | :--- |
| 주요 렌더링 위치 | 브라우저 | 서버 |
| 초기 콘텐츠 | JS 실행 이후 구성되는 경우가 많음 | 서버에서 생성한 HTML 제공 |
| SEO | 추가적인 고려가 필요할 수 있음 | 콘텐츠 수집에 유리할 수 있음 |
| 적합한 사례 | 대시보드, 관리 페이지 | 콘텐츠 사이트, 상품 상세 페이지 |

React는 CSR만 가능한 기술이 아니다.

Next.js와 같은 React 기반 프레임워크를 사용하면 SSR, 정적 페이지 생성 등 다양한 렌더링 방식을 활용할 수 있다.

이번 Todo List는 검색 엔진에 노출될 필요가 없고, 브라우저에서 할 일 목록을 그린 뒤 API로 데이터를 주고받는 구성으로 요구사항을 충족할 수 있다. 따라서 프론트엔드는 정적 파일로 배포하고, 화면은 브라우저에서 렌더링하는 CSR 방식을 선택했다.

### TypeScript는 왜 사용하는가?

TypeScript는 JavaScript에 정적 타입 검사 기능을 추가한 언어다.

JavaScript에서는 다음과 같은 코드가 실행될 수 있다.

```javascript
function add(a, b) {
  return a + b;
}

add(10, "20"); // "1020"
```

숫자의 덧셈을 의도했더라도 문자열이 전달되면 예상과 다른 결과가 발생할 수 있다.

TypeScript에서는 매개변수의 타입을 명시할 수 있다.

```typescript
function add(a: number, b: number): number {
  return a + b;
}

add(10, "20"); // 타입 오류
```

코드를 실행하기 전에 잘못된 타입 사용을 발견할 수 있다는 것이 장점이다.

특히 백엔드와 데이터를 주고받는 과정에서 데이터의 구조를 명확하게 정의할 수 있다.

```typescript
interface Todo {
  id: number;
  title: string;
  completed: boolean;
}
```

다만 TypeScript의 타입은 일반적으로 런타임에 제거된다.

따라서 백엔드에서 실제로 잘못된 데이터가 전달되는 상황까지 TypeScript가 자동으로 검증해주는 것은 아니다. 필요한 경우 별도의 런타임 검증도 해야 한다.

| 구분 | JavaScript | TypeScript |
| :--- | :--- | :--- |
| 타입 검사 | 주로 런타임에 타입 관련 문제 발견 | 정적 타입 검사 가능 |
| 초기 설정 | 비교적 간단함 | 타입 정의와 검사 환경 필요 |
| 개발 편의성 | 자유로운 구현 | 자동 완성, 타입 추론, 리팩터링 지원 |
| 선택 기준 | 간단한 스크립트, 빠른 실험 | 데이터 구조가 복잡하거나 유지보수가 중요한 프로젝트 |

### Vite는 왜 사용하는가?

Vite는 프론트엔드 개발 환경과 빌드 과정을 지원하는 도구다.

React는 UI를 구현하는 기술이고, TypeScript는 타입 검사를 지원하는 언어다.

하지만 작성한 코드를 개발 환경에서 실행하고, 브라우저에서 사용할 수 있는 형태로 변환하는 과정도 필요하다.

Vite는 이러한 작업을 지원한다.

**개발 환경**

```text
React / TypeScript 코드 작성
            ↓
      Vite 개발 서버
            ↓
      브라우저에서 확인
```

**배포 환경**

```text
React / TypeScript 소스 코드
            ↓
         Vite Build
            ↓
      HTML / CSS / JS
            ↓
      Web Server에 배포
```

Vite는 개발 서버와 HMR(Hot Module Replacement)을 제공해 코드 변경 사항을 빠르게 확인할 수 있도록 돕는다.

또한 프로덕션 빌드를 통해 배포에 필요한 정적 파일을 생성한다.

대표적인 빌드 관련 도구를 비교하면 다음과 같다.

| 기술 | 특징 |
| :--- | :--- |
| Vite | 빠른 개발 서버와 간편한 프론트엔드 프로젝트 구성 |
| Webpack | 세부적인 번들링 설정과 다양한 플러그인 |
| Parcel | 별도의 설정을 최소화한 프로젝트 구성 |

Vite 자체가 TypeScript의 모든 타입 오류를 검사하는 것은 아니다. 따라서 TypeScript 프로젝트에서는 별도의 타입 검사 과정도 필요하다.

### 이번 프로젝트의 선택 — React, TypeScript, Vite

이번 프로젝트에서는 다음과 같이 프론트엔드 기술을 선정했다.

| 기술 | 선정 이유 |
| :--- | :--- |
| React | 기존 프로젝트에서 사용한 경험 활용 |
| TypeScript | API 응답 및 컴포넌트의 데이터 구조 관리 |
| Vite | 간편한 개발 환경 구축과 정적 파일 빌드 |

이번 프로젝트에서는 새로운 프론트엔드 프레임워크를 학습하는 것보다 백엔드, 데이터베이스, 인프라까지 경험하는 것이 중요하다.

따라서 프론트엔드는 기존에 사용해봤던 기술을 선택해 학습 부담을 줄이려고 한다.

**익숙한 기술을 선택하는 것도 프로젝트의 목적에 따라 충분히 합리적인 판단이라는 것을 알게 되었다.**

## 4. Backend — 요청 처리와 비즈니스 로직

### Backend란 무엇인가?

백엔드는 클라이언트의 요청을 받아 필요한 로직을 처리하고 결과를 반환하는 영역이다.

Todo List에서 사용자가 새로운 할 일을 추가한다고 가정해보자.

```text
Frontend
   ↓ 할 일 추가 요청
Backend
   ↓ 요청 데이터 검증
   ↓ 비즈니스 로직 처리
Database
   ↓ 데이터 저장
Backend
   ↓ 처리 결과 응답
Frontend
   ↓ 화면 갱신
```

프론트엔드는 사용자의 입력을 받아 요청을 보내고, 백엔드는 요청이 유효한지 판단하고 데이터를 처리한다.

백엔드의 주요 역할은 다음과 같다.

- HTTP 요청 및 응답 처리
- 비즈니스 로직 실행
- 데이터베이스 접근
- 인증 및 인가
- 데이터 검증 및 예외 처리

여기서 비즈니스 로직이란 서비스가 지켜야 하는 규칙과 처리 방식을 의미한다.

예를 들어 Todo List에서 제목이 비어 있는 할 일은 생성할 수 없도록 하거나, 다른 사용자의 할 일을 수정할 수 없도록 하는 규칙이 해당한다.

프론트엔드에서도 입력값을 검증할 수 있지만, 클라이언트의 요청은 조작될 수 있으므로 중요한 규칙은 백엔드에서도 검증해야 한다.

### REST API란 무엇인가?

HTTP는 클라이언트와 서버가 요청과 응답을 주고받는 통신 프로토콜이다. REST(Representational State Transfer)는 네트워크 기반 애플리케이션을 설계하는 아키텍처 스타일이다. 웹에서는 HTTP 위에서 자원을 중심으로 API를 설계하는 데 REST의 원칙을 적용할 수 있다.

**REST API의 핵심 구성 3가지**

1. **자원(Resource)**은 API가 다루는 대상이며, URI로 식별한다. `/api/todos`는 할 일 목록을, `/api/todos/1`은 1번 할 일을 가리킨다.
2. **행위(HTTP 메서드)**는 자원에 수행할 작업을 나타낸다. 같은 URI라도 HTTP 메서드에 따라 다른 작업을 수행할 수 있다.
   - `GET`으로 자원을 조회한다.
   - `POST`는 새 자원을 생성할 때 주로 사용한다.
   - `PUT`으로 자원 전체를 교체하고, `PATCH`로 일부를 수정한다.
   - `DELETE`로 자원을 삭제한다.
3. **표현(Representation)**은 자원의 상태를 요청이나 응답에서 전달하는 형태다. 웹 API에서는 구조가 단순하고 읽기 쉬운 JSON을 흔히 사용한다.

이 구성을 Todo List API에 적용하면 다음과 같다.

| HTTP Method | URI | 역할 |
| :--- | :--- | :--- |
| GET | /api/todos | 전체 할 일 조회 |
| GET | /api/todos/1 | 특정 할 일 조회 |
| POST | /api/todos | 할 일 생성 |
| PATCH | /api/todos/1 | 할 일 일부 수정 |
| DELETE | /api/todos/1 | 할 일 삭제 |

예를 들어 프론트엔드에서 할 일을 추가하기 위해 다음과 같은 요청을 보낼 수 있다.

```http
POST /api/todos HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 60

{
  "title": "Spring Boot 공부",
  "completed": false
}
```

백엔드는 요청을 처리하고 데이터베이스에 저장한 뒤 응답을 반환한다.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 1,
  "title": "Spring Boot 공부",
  "completed": false
}
```

프론트엔드는 이 응답을 바탕으로 화면을 갱신할 수 있다.

### 백엔드 언어와 프레임워크

백엔드를 구현하는 방법은 다양하다.

Java, JavaScript, TypeScript, Python, Go 등 여러 프로그래밍 언어를 사용할 수 있으며, 각 언어에는 서버 개발을 지원하는 프레임워크가 존재한다.

| 언어 | 대표적인 프레임워크 |
| :--- | :--- |
| Java | Spring Boot |
| JavaScript / TypeScript | Express, NestJS |
| Python | Django, FastAPI |
| C# | ASP.NET Core |
| Go | Gin, Echo |

여기서 프로그래밍 언어와 프레임워크는 구분해야 한다.

Java는 프로그래밍 언어이고, Spring Boot는 Java 기반의 Spring 애플리케이션을 쉽게 구성하고 실행할 수 있도록 돕는 기술이다.

Node.js 역시 프로그래밍 언어가 아니라 JavaScript를 브라우저 외부에서 실행할 수 있게 하는 런타임 환경이다.

```text
Java (언어)
  └── JVM (런타임 환경)
       └── Spring Boot 애플리케이션 (프레임워크)

JavaScript / TypeScript (언어)
  └── Node.js (런타임 환경)
       └── Express / NestJS 애플리케이션 (프레임워크)

Python (언어)
  └── Python Runtime (런타임 환경)
       └── Django / FastAPI 애플리케이션 (프레임워크)
```

TypeScript를 Node.js에서 사용하는 경우에는 일반적으로 JavaScript로 변환하거나 TypeScript 실행을 지원하는 환경을 활용한다.

### 대표적인 백엔드 프레임워크 비교

| 기술 | 선택을 고려할 상황 | 고려할 점 |
| :--- | :--- | :--- |
| Spring Boot | 체계적인 서버 구조, 트랜잭션, 복잡한 비즈니스 로직 | Java와 Spring 생태계 학습 비용 |
| Express | 간단한 API, 자유로운 서버 구조 | 프로젝트 구조와 규칙을 직접 설계해야 함 |
| NestJS | TypeScript 기반의 구조화된 서버 개발 | Node.js와 프레임워크 구조에 대한 이해 필요 |
| Django | 인증, ORM, 관리자 기능을 활용한 빠른 개발 | 프레임워크가 제공하는 구조에 대한 이해 필요 |
| FastAPI | API 중심 서비스, Python 및 AI 시스템 연동 | 필요한 서비스 구조와 추가 기능을 직접 구성할 수 있음 |

### Spring Boot의 계층형 구조

Spring Boot를 공부하면서 가장 먼저 접한 개념 중 하나가 Controller, Service, Repository로 구성된 계층형 구조다.

```text
Client
   ↓ HTTP Request
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

| 계층 | 역할 |
| :--- | :--- |
| Controller | HTTP 요청을 받고 응답을 반환 |
| Service | 비즈니스 로직 처리 |
| Repository | 데이터베이스 접근 |
| Database | 데이터 저장 및 관리 |

예를 들어 할 일을 생성하는 기능을 구현한다면 Controller는 요청을 받고, Service는 생성 조건을 검증하고, Repository는 데이터를 저장하는 역할을 담당할 수 있다.

이렇게 역할을 분리하면 각 계층이 담당하는 책임이 명확해지고, 코드를 수정하거나 테스트하기 쉬워진다.

물론 모든 Spring Boot 프로젝트가 반드시 이러한 구조를 사용해야 하는 것은 아니다.

하지만 이번 프로젝트에서는 **백엔드의 기본적인 책임 분리와 구조 설계**를 학습하기 위해 계층형 구조를 적용하려고 한다.

### 이번 프로젝트의 선택 — Java 21, Spring Boot

Todo List의 기능만 고려하면 Spring Boot가 반드시 필요한 것은 아니다.

기존에 사용하던 TypeScript를 활용해 NestJS로 구현하거나, Python 기반의 FastAPI를 사용해도 충분하다.

하지만 이번 프로젝트에서는 다음과 같은 개념을 학습하고 싶었다.

- Java 기반의 객체지향 프로그래밍
- Controller, Service, Repository의 책임 분리
- 의존성 주입(DI)
- ORM과 JPA를 활용한 데이터베이스 접근
- 트랜잭션 관리
- 백엔드 테스트

Java 21은 장기 지원(LTS) 버전이며, 현재 구성한 Java 개발 환경을 그대로 활용할 수 있다는 점도 고려했다.

이번에는 익숙한 기술을 사용해 빠르게 개발하는 것보다 새로운 기술을 통해 백엔드의 기본 구조를 학습하는 것을 우선했다.

## 5. Database — 데이터의 저장과 관리

### Database란 무엇인가?

데이터베이스는 데이터를 체계적으로 저장하고 관리하기 위한 데이터의 집합이다.

프론트엔드에서 다음과 같이 할 일 목록을 관리한다고 가정해보자.

```javascript
const todos = [
  { id: 1, title: "React 공부", completed: false },
  { id: 2, title: "Java 공부", completed: true }
];
```

이 데이터를 메모리에서만 관리한다면 페이지를 새로고침하거나 애플리케이션이 종료되었을 때 변경 사항이 사라질 수 있다.

LocalStorage를 사용하면 브라우저에 데이터를 유지할 수 있지만, 여러 기기에서 동일한 데이터를 공유하거나 여러 사용자의 데이터를 중앙에서 관리하기에는 한계가 있다.

그래서 일반적인 서버 기반 웹 서비스에서는 데이터베이스를 활용한다.

### Database와 DBMS의 차이

데이터베이스를 공부하면서 먼저 구분해야 하는 개념이 있다.

| 구분 | 의미 |
| :--- | :--- |
| Database | 체계적으로 저장된 데이터의 집합 |
| DBMS | 데이터베이스를 생성하고 관리하는 소프트웨어 |
| SQL | 관계형 데이터베이스의 데이터를 정의하고 조작하는 언어 |

PostgreSQL과 MySQL은 데이터베이스를 관리하는 DBMS(Database Management System)다.

이번 프로젝트의 데이터 구조를 예로 들면 다음과 같다.

```text
PostgreSQL (DBMS)
    │
    └── todo_db (Database)
          │
          └── public (Schema)
                │
                └── todos (Table)
                      ├── id
                      ├── title
                      ├── completed
                      └── created_at
```

PostgreSQL이라는 DBMS를 통해 `todo_db`라는 데이터베이스를 관리하고, 그 안에 할 일 데이터를 저장할 테이블을 생성하는 것이다.

### RDBMS와 NoSQL

데이터베이스 기술을 선택하기 위해서는 데이터가 어떤 형태로 저장되고 관리되는지 이해해야 한다.

대표적으로 관계형 데이터베이스와 NoSQL 데이터베이스가 있다.

**RDBMS(Relational Database Management System)**

관계형 데이터베이스를 관리하는 시스템이다.

데이터를 테이블 형태로 관리하고, 기본키와 외래키 등을 활용해 데이터 간 관계를 표현할 수 있다.

예를 들어 사용자와 할 일 데이터를 다음과 같이 구성할 수 있다.

**users**

| id (PK) | name |
| :--- | :--- |
| 1 | User A |
| 2 | User B |

**todos**

| id (PK) | user_id (FK) | title |
| :--- | :--- | :--- |
| 1 | 1 | React 공부 |
| 2 | 1 | Java 공부 |
| 3 | 2 | PostgreSQL 공부 |

한 명의 사용자는 여러 개의 할 일을 가질 수 있다.

```text
Users (1)
    │
    │ 1:N
    │
Todos (N)
```

`todos` 테이블의 `user_id`는 `users` 테이블의 `id`를 참조하는 외래키다.

이러한 관계를 활용해 1번 사용자의 할 일 목록을 조회할 수 있다.

```sql
SELECT users.name, todos.title
FROM users
JOIN todos
    ON users.id = todos.user_id
WHERE users.id = 1;
```

대표적인 RDBMS에는 PostgreSQL, MySQL, MariaDB, SQLite 등이 있다.

**NoSQL**

NoSQL은 관계형 데이터베이스 이외의 다양한 데이터 모델을 사용하는 데이터베이스를 통칭한다.

대표적인 유형은 다음과 같다.

| 유형 | 대표 기술 | 특징 |
| :--- | :--- | :--- |
| Document | MongoDB | 문서 형태로 데이터 관리 |
| Key-Value | Redis | 키를 기준으로 값에 접근 |
| Wide-Column | Cassandra | 분산 환경의 대규모 데이터 처리 |
| Graph | Neo4j | 노드와 관계 중심의 데이터 관리 |

예를 들어 MongoDB에서는 사용자와 할 일 정보를 하나의 문서에 포함하는 방식으로 모델링할 수 있다.

```json
{
  "id": 1,
  "name": "User A",
  "todos": [
    {
      "title": "React 공부",
      "completed": false
    },
    {
      "title": "Java 공부",
      "completed": true
    }
  ]
}
```

관계형 데이터베이스에서는 별도의 테이블로 분리했던 데이터를 문서 내부에 포함한 예시다.

물론 MongoDB에서도 데이터를 여러 컬렉션으로 분리하고 참조할 수 있다.

중요한 것은 어떤 방식이 무조건 더 좋다는 것이 아니라, 데이터의 구조와 조회 패턴에 따라 적절한 모델링 방식이 달라진다는 점이다.

### RDBMS와 NoSQL의 선택 기준

| 구분 | RDBMS | NoSQL |
| :--- | :--- | :--- |
| 데이터 모델 | 관계형 테이블 | 문서, 키-값, 그래프 등 |
| 스키마 | 일반적으로 명시적인 구조 | 유형에 따라 유연한 구조 |
| 데이터 관계 | JOIN, 외래키 등을 활용 | 참조, 중첩 문서 등 모델별 방식 |
| 데이터 정합성 | 제약조건과 트랜잭션 활용 | 제품별로 지원 방식이 다름 |
| 선택 기준 | 명확한 데이터 관계와 정합성이 중요한 경우 | 특정 데이터 모델이나 접근 패턴이 중요한 경우 |

NoSQL이라고 해서 트랜잭션을 지원하지 않는 것은 아니며, RDBMS라고 해서 유연한 데이터 구조를 저장할 수 없는 것도 아니다.

예를 들어 PostgreSQL은 JSON 데이터를 저장하고 조회할 수 있는 기능을 제공하고, MongoDB도 여러 문서에 걸친 트랜잭션을 지원한다.

따라서 RDBMS와 NoSQL을 단순히 정형 데이터와 비정형 데이터의 차이로만 구분하기보다는 서비스에서 데이터를 어떻게 저장하고 조회할 것인지 고려해야 한다.

### 대표적인 데이터베이스 비교

| 기술 | 유형 | 선택을 고려할 상황 |
| :--- | :--- | :--- |
| PostgreSQL | RDBMS | 복잡한 쿼리, 데이터 정합성, 다양한 데이터 타입과 확장 기능 |
| MySQL | RDBMS | 일반적인 웹 서비스, 익숙한 운영 환경과 생태계 |
| SQLite | 임베디드 RDBMS | 로컬 애플리케이션, 소규모 서비스, 간단한 운영 |
| MongoDB | Document DB | 문서 중심의 데이터 구조와 유연한 모델링 |
| Redis | 인메모리 중심 데이터 저장소 | 캐싱, 세션 관리, 빠른 키 기반 접근 |

여기서 SQLite는 PostgreSQL이나 MySQL과 실행 구조가 다르다.

PostgreSQL은 일반적으로 별도의 데이터베이스 서버 프로세스를 실행하고, 애플리케이션이 해당 서버에 연결하는 방식으로 사용한다.

```text
Application
     ↓ Database Connection
PostgreSQL Server
     ↓
Disk Storage
```

반면 SQLite는 별도의 데이터베이스 서버 프로세스 없이 애플리케이션에서 라이브러리를 통해 데이터베이스 파일에 접근하는 방식으로 사용할 수 있다.

```text
Application
     ↓
SQLite Library
     ↓
Database File
```

따라서 간단한 서비스라면 SQLite를 선택해 데이터베이스 서버를 운영하는 부담을 줄일 수도 있다.

### 데이터 정합성과 트랜잭션

**데이터 정합성**은 저장된 데이터가 서비스의 규칙에 맞는 상태를 유지하는 것을 뜻한다. 예를 들어 Todo List에서 모든 할 일은 실제로 존재하는 사용자의 것이어야 하고, 제목에는 공백 이외의 문자가 있어야 한다.

관계형 데이터베이스에서는 **제약조건**으로 이런 규칙을 지킬 수 있다. 예를 들어 할 일의 사용자 ID에 외래 키를 설정하면 존재하지 않는 사용자의 ID를 저장하려는 요청을 데이터베이스가 거부한다.

| 제약조건 | 적용 예시 |
| :--- | :--- |
| PRIMARY KEY | 할 일마다 고유한 ID를 부여한다. |
| FOREIGN KEY | 할 일의 사용자 ID가 실제 사용자 행을 가리키도록 한다. |
| NOT NULL | 제목에 `NULL`이 들어가는 것을 막는다. |
| UNIQUE | 여러 사용자가 같은 이메일 주소를 등록하는 것을 막는다. |
| CHECK | 제목 양쪽의 공백을 제거했을 때 글자가 하나 이상 남도록 검사한다. |

여러 변경이 함께 적용되어야 지킬 수 있는 규칙도 있다. 예를 들어 Todo List에 **할 일을 완료하면 완료 기록도 남기는 기능**을 추가한다고 가정해보자. 이 기능은 데이터베이스에서 두 가지 작업을 수행한다.

1. 할 일의 상태를 완료로 바꾼다.
2. 누가 언제 완료했는지 기록을 추가한다.

첫 번째 변경이 이미 저장된 뒤 두 번째 작업이 실패하면, 화면에는 할 일이 완료로 표시되지만 완료 기록은 비어 있게 된다.

**트랜잭션**은 이렇게 함께 처리해야 할 작업을 하나로 묶는 단위다. 두 작업이 모두 성공하면 `COMMIT`으로 변경을 확정한다. 완료 기록을 추가하는 데 실패하면 `ROLLBACK`으로 이번 트랜잭션에서 바꾼 완료 상태도 되돌린다.

트랜잭션의 주요 특성인 **ACID**도 같은 예시로 살펴볼 수 있다.

| 특성 | Todo List 예시 |
| :--- | :--- |
| Atomicity (원자성) | 완료 상태 변경과 기록 추가가 둘 다 반영되거나 둘 다 반영되지 않는다. |
| Consistency (일관성) | 트랜잭션이 끝난 뒤에도 완료 기록이 실제로 존재하는 할 일을 가리키는 등 정의된 데이터 규칙이 지켜진다. |
| Isolation (격리성) | 여러 요청이 동시에 실행될 때 중간 변경을 다른 요청이 볼 수 있는지 등 요청 간 간섭을 제어한다. |
| Durability (지속성) | 완료 처리와 기록이 커밋되면 데이터베이스가 장애에서 복구된 뒤에도 그 결과가 남는다. |

이번 Todo List에서 할 일의 완료 상태만 바꾼다면 한 번의 갱신으로 처리할 수 있다. 나중에 완료 기록처럼 함께 저장해야 하는 데이터가 생기면, 관련 작업을 하나의 트랜잭션으로 묶을 수 있다.

### 데이터 영속성(Persistence)

데이터 영속성이란 데이터를 생성한 프로그램이 종료된 이후에도 해당 데이터가 유지되는 성질을 의미한다.

일반적인 메모리 기반 상태와 디스크에 저장되는 데이터는 다음과 같은 차이가 있다.

```text
메모리에 저장된 애플리케이션 상태
    ↓
프로세스 종료
    ↓
상태 소멸
```

```text
데이터베이스에 정상적으로 저장된 데이터
    ↓
데이터베이스 서비스 종료
    ↓
서비스 재시작
    ↓
저장된 데이터 조회
```

이번 프로젝트에서는 PostgreSQL을 설치한 뒤 SQL을 직접 작성해 CRUD를 수행하고, 데이터베이스 서비스 재시작 이후에도 데이터가 유지되는지 검증했다.

```text
INSERT
   ↓
SELECT
   ↓
PostgreSQL 재시작
   ↓
SELECT
   ↓
데이터 유지 확인
```

단순히 데이터가 저장된다는 설명을 읽는 것보다 직접 재시작하고 데이터를 조회해보니 애플리케이션의 실행 상태와 데이터의 저장 상태가 별개라는 점을 이해하기 쉬웠다.

다만 정상적인 서비스 재시작 이후 데이터가 유지된다고 해서 갑작스러운 전원 차단이나 디스크 장애 상황까지 모두 검증한 것은 아니다.

실제 운영 환경에서는 장애 복구, 백업, 데이터 복제 등도 별도로 고려해야 한다.

### 이번 프로젝트의 선택 — PostgreSQL

Todo List의 데이터는 구조가 비교적 명확하다.

```text
Todo
 ├── id
 ├── title
 ├── completed
 └── created_at
```

추후 사용자 기능이 추가된다면 사용자와 할 일 사이의 관계도 표현할 수 있다.

따라서 관계형 데이터베이스를 선택하는 것이 자연스럽다고 판단했다.

이번에는 관계형 데이터 모델을 설계하고, 애플리케이션을 별도의 데이터베이스 서버에 연결해 운영하는 과정을 경험하고 싶었다. SQLite로도 할 일 데이터를 저장할 수 있지만, 별도의 서버를 설치하고 접속 권한을 관리하는 과정까지 경험하려면 PostgreSQL이나 MySQL 같은 서버형 DBMS가 학습 목표에 더 잘 맞는다.

이 프로젝트에서는 그 조건을 충족하는 PostgreSQL을 선택했다. PostgreSQL 서버를 직접 구성하고, 사용자와 접근 권한을 설정한 뒤 Spring Boot에서 연결하는 과정을 학습 범위에 포함했다.

## 6. Frontend, Backend, Database는 어떻게 연결되는가?

지금까지 세 가지 기술 영역을 각각 살펴봤다.

하지만 실제 서비스에서는 이 기술들이 독립적으로 동작하는 것이 아니라 서로 연결되어 하나의 기능을 구현한다.

Todo List에서 할 일을 추가하는 과정을 예로 들어보자.

```text
[User]
할 일 입력 및 추가 버튼 클릭
        ↓
[React]
사용자 입력값 처리
        ↓
HTTP POST /api/todos
        ↓
[Spring Boot Controller]
요청 수신
        ↓
[Spring Boot Service]
데이터 검증 및 비즈니스 로직
        ↓
[Spring Boot Repository]
데이터베이스 접근
        ↓
[PostgreSQL]
데이터 저장
        ↓
[Spring Boot]
저장 결과를 JSON으로 반환
        ↓
[React]
응답 데이터로 상태 갱신
        ↓
[User]
새로운 할 일 확인
```

이 구조에서 각 기술은 서로 다른 문제를 해결한다.

React는 사용자 인터페이스를 관리하고, Spring Boot는 서비스의 규칙에 따라 요청을 처리하며, PostgreSQL은 데이터를 저장한다.

지금까지 프론트엔드에서 API를 호출할 때는 주로 어떤 데이터를 요청하고 어떤 응답을 받는지에 집중했다.

이번 프로젝트에서는 그 요청이 백엔드 내부에서 어떻게 처리되고, 데이터베이스에 어떤 방식으로 저장되는지까지 직접 구현해보려고 한다.
