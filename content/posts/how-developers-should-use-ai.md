# 개발자는 AI를 어떻게 대해야 할까 — AI는 신이 아니다

요즘 개발하면서 AI를 사용하지 않는 사람을 찾기가 더 어렵다.

개발자가 아니더라도 마찬가지다. 우리 부모님도 궁금한 것이 생기면 AI에게 물어보고, 검색 대신 AI를 사용하기도 한다. AI는 어느새 검색 도구를 넘어 친구, 동료, 선생님 같은 역할까지 맡고 있다.

나 역시 개발할 때 AI를 자주 사용한다.

다만 최근 AI를 사용하는 사람들을 보면서 한 가지 생각이 들었다.

> **개발자라면 AI를 사용하는 것보다, AI를 어떻게 사용하느냐가 더 중요하지 않을까?**

내가 생각하는 방향은 단순하다.

**AI는 내 뇌가 아니라, 내 손이어야 한다.**

---

## AI는 신이 아니다

AI와 자연스럽게 대화를 하다 보면 AI가 정말 생각하고 판단해서 답을 주는 것처럼 느껴진다.

하지만 적어도 우리가 흔히 사용하는 LLM은 사람과 같은 방식으로 생각하지 않는다.

대표적인 언어 모델은 주어진 문맥을 바탕으로 **다음에 올 토큰의 확률을 계산하고, 그 과정을 반복하면서 문장을 만들어낸다.**

아주 단순화하면 이런 흐름이다.

```text
입력된 문맥
    ↓
다음 토큰의 확률 계산
    ↓
가장 적절한 토큰 선택
    ↓
기존 문맥에 추가
    ↓
다음 토큰의 확률 계산
    ↓
반복
```

예를 들어,

```text
1, 2, 3, 4, ?
```

라는 문장이 주어진다면 `5`가 이어질 가능성이 매우 높다.

물론 실제 LLM의 동작은 이것보다 훨씬 복잡하다. 학습 과정에서는 방대한 데이터를 기반으로 모델의 파라미터가 조정되고, 이후 다양한 후처리와 학습 과정도 거친다.

내가 말하고 싶은 핵심은 이것이다.

**AI의 학습을 인간이 공부해서 지식을 이해하는 과정과 동일하게 생각하면 안 된다.**

AI가 매우 자연스럽게 설명한다고 해서 그 내용을 실제로 이해하고 있거나, 답이 반드시 사실이라는 의미도 아니다.

그래서 AI는 틀린 내용을 굉장히 그럴듯하게 이야기할 수도 있다.

일반 사용자는 이런 특성을 몰라도 AI를 사용할 수 있다.

하지만 개발자는 적어도 자신이 사용하는 도구가 어떤 성질을 가지고 있는지는 알아야 한다고 생각한다.

---

## AI를 뇌처럼 사용하지 말자

그래서 나는 AI를 **내 뇌가 아니라 손처럼 사용하려고 한다.**

코딩 에이전트에게 이런 요청을 하는 것을 별로 좋아하지 않는다.

```text
로그인 기능 만들어줘.
```

물론 나도 급하면 이렇게 사용할 때가 있다.

하지만 내가 추구하는 방식은 아니다.

이렇게 요청하면 인증 방식, 디렉터리 구조, 상태 관리 방법, 에러 처리 방식 등 수많은 결정을 AI가 대신하게 된다.

나는 그 반대의 방식을 선호한다.

```text
로그인 상태는 Zustand의 authStore에서 관리한다.

POST /api/auth/login
Request:
{
  email: string,
  password: string
}

성공 시 accessToken을 authStore에 저장한다.
401이면 "이메일 또는 비밀번호를 확인해주세요."를 출력한다.

LoginForm 컴포넌트의 submit 로직만 구현해줘.
기존 구조는 변경하지 마.
```

무엇을 만들지, 어떤 구조를 사용할지, 데이터가 어떻게 흘러갈지는 내가 결정한다.

AI는 그 결정에 따라 코드를 작성한다.

내가 AI 코드 에디터의 자동완성 기능을 좋아하는 것도 같은 이유다.

내가

```ts
function validateEmail(email: string) {
```

까지 작성했을 때 나머지 구현을 AI가 빠르게 완성해주는 방식이다.

방향은 내가 결정하고, 반복적인 작업 속도를 AI가 높여준다.

내가 생각하는 **AI를 손처럼 사용한다**는 것은 이런 의미다.

---

## 모르는 것을 AI에게 통째로 맡기지 않는다

내가 가장 경계하는 상황은 **내가 모르는 영역을 AI에게 통째로 맡기는 것**이다.

예를 들어 내가 Docker를 전혀 모르는 상태에서

```text
우리 프로젝트 Docker 환경 구축해줘.
```

라고 요청한다.

AI가 `Dockerfile`, `docker-compose.yml`, 네트워크 설정까지 모두 만들어줬고 실행도 잘 된다.

문제는 여기서 발생한다.

```yaml
services:
  frontend:
    build: ./frontend
    depends_on:
      - backend

  backend:
    build: ./backend
```

이 코드가 왜 이렇게 작성됐는지 설명하지 못한다면, 문제가 발생했을 때 내가 통제할 수 있는 영역이 아니다.

나는 AI를 사용하면 안 된다는 이야기를 하는 것이 아니다.

모른다면 오히려 AI를 적극적으로 사용할 수 있다.

다만 순서가 달라야 한다고 생각한다.

```text
모르는 영역
   ↓
AI에게 개념을 질문한다
   ↓
직접 이해한다
   ↓
구조와 방향을 결정한다
   ↓
AI에게 구현을 맡긴다
   ↓
결과를 검증한다
```

즉, 모르는 것을 바로 **위임**하기보다는 먼저 **학습**하는 데 AI를 사용하는 것이다.

적어도 AI가 작성한 코드를 내가 설명할 수 있는 수준까지는 이해하고 있어야 한다고 생각한다.

---

## 그래서 나는 바이브 코딩을 경계한다

나는 `바이브 코딩`이라는 말을 별로 좋아하지 않는다.

바이브 코딩 자체가 나쁘다는 뜻은 아니다.

아이디어를 빠르게 검증하거나 프로토타입을 만드는 상황에서는 굉장히 좋은 방법이라고 생각한다.

예를 들어 하루 안에 아이디어를 확인해야 한다면

```text
이런 서비스를 만들고 싶어.
React로 화면 만들고 API까지 연결해서
동작하는 프로토타입 만들어줘.
```

라고 요청해서 빠르게 결과물을 만드는 것은 충분히 가치가 있다.

문제는 이것을 **개발자의 기본 개발 방식으로 가져오는 것**이다.

AI가 만든 코드를 읽지 않고,

구조를 왜 그렇게 만들었는지 모르고,

문제가 발생하면 다시 AI에게 에러 메시지를 복사해서 보내고,

수정된 코드도 이해하지 않은 채 적용한다.

이 과정이 반복되면 개발자는 점점 시스템에 대한 통제권을 잃는다.

개발자가 AI를 사용하는 것과 일반 사용자가 AI를 사용하는 것의 차이는 결국 여기에서 나와야 한다고 생각한다.

**개발자는 결과만 받는 사람이 아니라 결과를 검증하고 통제할 수 있어야 한다.**

## AI 엔지니어링은 도구를 많이 쓰는 것이 아니다

최근에는 AI 개발 환경과 관련해서 `Rules`, `Skills`, `Context`, `Harness`, MCP 등 여러 개념이 등장하고 있다.

나도 이런 것들을 사용하고 있다.

다만 이런 도구를 사용한다는 것 자체가 AI 엔지니어링은 아니라고 생각한다.

GitHub에서 유명한 설정을 가져오고,

```text
이 내용을 우리 프로젝트에 맞게 수정해줘.
```

라고 AI에게 요청한 뒤 몇몇 문장만 바꾸는 것은 어렵지 않다.

중요한 것은 **왜 이 규칙이 필요한지를 설명할 수 있느냐**다.

예를 들어 Rules를 작성한다면 단순히 파일을 만드는 것이 아니라,

```md
# Frontend Rules

- API 호출은 components에서 직접 수행하지 않는다.
- API 로직은 services 디렉터리에서 관리한다.
- 서버 상태는 TanStack Query로 관리한다.
- 전역 UI 상태만 Zustand를 사용한다.
```

왜 이런 규칙을 설정했는지 설명할 수 있어야 한다.

```text
AI가 반복적으로 컴포넌트 내부에 API 로직을 작성한다.
        ↓
프로젝트 구조가 일관되지 않는다.
        ↓
AI가 지켜야 할 경계를 Rules로 정의한다.
        ↓
생성 결과의 편차를 줄인다.
```

이런 문제와 해결 과정이 있어야 Rules를 사용하는 의미가 생긴다.

결국 AI 엔지니어링도 일반적인 소프트웨어 엔지니어링과 크게 다르지 않다고 생각한다.

도구 자체보다 **문제를 정의하고, 기준을 만들고, 결과를 검증하는 과정**이 중요하다.

## 내가 생각하는 개발자의 AI 사용 기준

내 기준은 세 가지다.

### 1. 내가 설명할 수 있는 영역에서 사용한다

AI가 작성한 코드를 보고

> 왜 이렇게 작성됐나요?

라는 질문을 받았을 때 설명할 수 있어야 한다.

설명하지 못한다면 내 코드라고 보기 어렵다.

### 2. 결정은 내가 하고, 구현 속도를 AI로 높인다

아키텍처, 상태 관리 방식, 데이터 흐름처럼 프로젝트의 방향을 결정하는 부분은 가능하면 직접 판단한다.

AI에게는 그 안에서 반복적인 구현이나 리팩터링, 테스트 작성 등을 맡긴다.

```text
사람
→ 무엇을 만들 것인가
→ 어떤 구조로 만들 것인가
→ 어떤 기준으로 검증할 것인가

AI
→ 코드 작성
→ 반복 작업
→ 테스트 케이스 생성
→ 리팩터링 보조
→ 문서화
```

이런 형태가 내가 생각하는 이상적인 역할 분담이다.

### 3. 모르는 것은 먼저 배운 뒤 맡긴다

내가 모르는 영역이라면 AI에게 바로 구현을 요청하기보다 먼저 질문한다.

그리고 최소한 결과물을 검증할 수 있는 수준까지 이해한 다음 AI를 사용한다.

결국 기준은 하나다.

> **AI가 내 통제 범위 안에 있는가?**

나는 이 기준을 가장 중요하게 생각한다.

---

## 그렇다면 AI에게 무엇을 맡기면 좋을까?

이 생각을 하다 보니 AI에게 꽤 잘 맞는 일이 하나 떠올랐다.

**테스트 코드다.**

기능의 요구사항과 기대 결과는 개발자가 정의한다.

```ts
function add(a: number, b: number): number
```

그리고 내가 동작을 정의한다.

```text
add(1, 2) → 3
add(-1, 1) → 0
add(0, 0) → 0
```

그다음 테스트 코드를 작성하거나 반복적인 테스트 케이스를 확장하는 작업은 AI에게 맡길 수 있다.

```ts
describe('add', () => {
  it('두 양수를 더한다.', () => {
    expect(add(1, 2)).toBe(3);
  });

  it('음수와 양수를 더한다.', () => {
    expect(add(-1, 1)).toBe(0);
  });

  it('0과 0을 더한다.', () => {
    expect(add(0, 0)).toBe(0);
  });
});
```

여기서 중요한 것은 테스트의 기준을 AI가 결정한 것이 아니라 **내가 기대하는 동작을 먼저 정의했다는 점**이다.

AI는 그 기준을 코드로 만드는 일을 도와준다.

내가 앞에서 이야기했던

> **AI를 뇌가 아니라 손처럼 사용한다.**

라는 방식과 꽤 잘 맞는다.

## 마무리

AI를 멀리하자는 이야기가 아니다.

오히려 나는 앞으로 개발자가 AI를 얼마나 잘 활용하느냐가 생산성에 큰 차이를 만들 것이라고 생각한다.

다만 AI가 강력해질수록 개발자에게 필요한 능력도 조금 달라질 것 같다.

코드를 직접 몇 줄 더 작성하는 능력보다

**무엇을 만들어야 하는지 결정하고, AI에게 정확하게 일을 나누고, 결과를 검증하고, 문제가 생겼을 때 다시 통제권을 가져올 수 있는 능력**이 더 중요해질 수 있다.

그래서 나는 AI에게 내 판단까지 넘기기보다는, 내가 내린 판단을 더 빠르게 실행하기 위한 도구로 사용하려고 한다.

**AI는 내 뇌가 아니라 내 손이다.**

그리고 이 생각이 실제 개발에서도 유효한지 직접 확인해보려고 한다.

이번 주에는 AI를 활용한 TDD 방식으로 개발을 진행해볼 생각이다.

다음 글에서는 실제로 어떤 방식으로 AI에게 테스트를 작성시키고, 그 과정에서 어떤 점이 좋았고 어떤 문제가 있었는지 정리해보려고 한다.
