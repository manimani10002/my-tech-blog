# Product Engineer, 결국 풀스택 개발자가 되어야 할까?

> AI 시대, 프론트엔드 개발자를 준비하는 나는 어디까지 개발할 수 있어야 할까?

최근 채용공고를 살펴보면서 개발자의 역할이 점점 넓어지고 있다는 느낌을 받았다.

프론트엔드 개발자에게 백엔드 경험을 요구하고, 백엔드 개발자에게도 웹 전반에 대한 이해를 기대한다. 직무 구분은 여전히 존재하지만 실제 업무에서 요구하는 기술의 경계는 점점 흐려지고 있다.

특히 AI가 개발 과정에 들어오면서 개발자 한 명이 다룰 수 있는 기술의 범위도 넓어지고 있다.

이런 변화를 살펴보던 중 **Product Engineer(PE)** 라는 직무를 알게 되었다.

그리고 한 가지 질문이 생겼다.

**앞으로 개발자는 자신의 전문 분야를 넘어, 서비스 전체를 구현할 수 있는 풀스택 역량을 갖춰야 하지 않을까?**

---

## Product Engineer란 무엇일까?

최근 무신사는 기존 서버, 웹, 모바일로 구분했던 개발 직군을 **Product Engineer(PE)** 로 통합했다.

처음 이 소식을 접했을 때는 단순히 프론트엔드와 백엔드를 모두 다루는 풀스택 개발자를 의미한다고 생각했다.

하지만 PE는 기술의 범위뿐 아니라 **제품의 문제를 발견하고 해결한 뒤, 그 결과까지 책임지는 역할**에 더 가깝다.

기존 개발자의 업무를 단순화하면 다음과 같다.

```
요구사항 전달
      ↓
담당 기능 구현
      ↓
개발 완료
```

반면 PE가 지향하는 개발 과정은 조금 더 넓다.

```
문제 발견 및 정의
       ↓
해결 방법 결정
       ↓
설계 및 구현
       ↓
배포 및 운영
       ↓
결과 확인 및 개선
```

물론 기존 개발자가 문제 정의나 제품 개선에 참여하지 않았다는 의미는 아니다. PE는 이러한 책임을 개발자의 핵심 역할로 더욱 강조하는 개념이라고 이해했다.

단순히 **'어떻게 구현할 것인가?'** 를 넘어 **'무엇을 왜 해결해야 하는가?'** 까지 고민하는 것이다.

---

## Product Engineer는 풀스택 개발자인가?

PE와 풀스택 개발자는 엄밀히 말하면 다른 개념이다.

풀스택 개발자가 **다룰 수 있는 기술의 범위**를 의미한다면, PE는 **제품에 대해 책임지는 범위**에 가깝다.

그렇다면 PE에게 풀스택 역량이 필요할까?

모든 PE가 프론트엔드와 백엔드의 전문가여야 하는 것은 아닐 것이다.

하지만 나는 **풀스택 역량이 PE를 지향하기 위한 중요한 기술적 기반**이라고 생각한다.

예를 들어 사용자가 Todo List에서 할 일을 저장했는데, 새로고침하면 데이터가 사라지는 문제가 발생했다고 가정해보자.

원인은 여러 곳에 있을 수 있다.

```
Frontend
  ├─ 상태 관리 문제
  └─ API 호출 문제

Backend
  ├─ 요청 처리 문제
  └─ 비즈니스 로직 문제

Database
  └─ 데이터 저장 문제

Infrastructure
  └─ 서버 및 연결 설정 문제
```

프론트엔드만 알고 있다면 자신이 담당한 영역부터 확인할 것이다.

하지만 백엔드와 데이터베이스의 동작까지 이해한다면 문제를 더 넓은 관점에서 추적할 수 있다.

직접 수정할 수 있는 범위도 넓어진다.

내가 풀스택 역량을 갖추려는 이유는 단순히 여러 기술을 사용할 수 있다는 것을 보여주기 위해서가 아니다.

**제품의 문제를 해결할 때 기술적인 경계가 나의 한계가 되지 않도록 하기 위해서다.**

---

## AI는 개발자의 기술적 경계를 낮추고 있다

이러한 변화에서 AI의 영향도 크다고 생각한다.

과거에는 익숙하지 않은 기술로 새로운 기능을 구현하려면 상당한 학습 시간이 필요했다.

지금은 AI를 활용해 프로젝트 구조를 설계하고, API를 작성하고, 데이터베이스를 연결하는 작업까지 빠르게 진행할 수 있다.

프론트엔드 개발자가 백엔드에 접근하는 진입 장벽도 낮아진 것이다.

하지만 여기서 중요한 질문이 있다.

> AI가 코드를 작성할 수 있다는 것과 내가 그 코드를 이해하고 다룰 수 있다는 것은 같은가?

나는 아니라고 생각한다.

예를 들어 AI가 Spring Boot로 REST API를 작성해줬다고 가정해보자.

API가 정상적으로 동작하더라도 다음 과정을 이해하지 못한다면 문제가 발생했을 때 원인을 판단하기 어렵다.

```
HTTP Request
      ↓
Controller
      ↓
Service
      ↓
Repository
      ↓
Database
      ↓
HTTP Response
```

AI가 작성한 코드를 사용하는 것과 그 코드의 동작을 이해하고 책임지는 것은 다르다.

지난 글에서 나는 **'AI는 뇌가 아니라 손이어야 한다'** 는 생각을 이야기했다.

이번에도 같은 관점이다.

AI를 통해 개발 속도를 높이고 새로운 기술 영역으로 확장할 수는 있다. 하지만 결과물을 검증하고 통제하려면 개발자 스스로 기본적인 구조와 원리를 이해해야 한다.

**AI가 개발자의 기술적 경계를 낮춰줄 수는 있지만, 개발자의 이해까지 대신해주지는 않는다.**

---

## 그렇다면 모든 기술을 공부해야 할까?

여기서 현실적인 고민이 생겼다.

나는 지금까지 프론트엔드를 중심으로 공부해왔다.

React와 TypeScript만 놓고 봐도 렌더링, 상태 관리, 브라우저 동작, 성능 최적화처럼 더 깊게 공부해야 할 것이 많다.

그런데 여기에 백엔드, 데이터베이스, 인프라까지 공부해야 한다면 어느 하나도 제대로 하지 못하는 것은 아닐까?

그래서 학습 방향을 정했다.

**프론트엔드를 주력으로 유지하되, 서비스 전체를 직접 구현할 수 있는 개발자가 되자.**

```
       Frontend
     (주력 전문성)
           │
    ┌──────┴──────┐
    │             │
 Backend       Database
    │             │
    └──────┬──────┘
           │
    Infrastructure
           │
         CI/CD
```

모든 기술을 동일한 깊이로 공부하겠다는 의미는 아니다.

프론트엔드는 계속 깊게 공부하면서, 백엔드부터 배포까지는 기본적인 서비스를 독립적으로 구현할 수 있는 수준을 목표로 한다.

프론트엔드 전문성을 포기하는 것이 아니라 **프론트엔드를 중심으로 해결할 수 있는 문제의 범위를 넓히는 것**이다.

---

## 그래서 E2E 개발을 시작했다

지금까지 팀 프로젝트에서는 주로 프론트엔드 개발을 담당했다.

API 연동, 상태 관리, UI 구현은 경험했지만 백엔드와 데이터베이스를 직접 구축하고 서비스를 배포하는 경험은 상대적으로 부족했다.

그래서 작은 서비스를 하나 직접 E2E(End-to-End)로 개발해보기로 했다.

서비스는 **Todo List**다.

복잡한 기능이나 새로운 아이디어는 필요하지 않다.

이번 프로젝트의 목표는 좋은 Todo 서비스를 만드는 것이 아니라, **프론트엔드부터 배포까지 전체 개발 과정을 직접 경험하는 것**이다.

### 기술 스택

| 영역         | 기술                      |
| ---------- | ----------------------- |
| Frontend   | React, TypeScript, Vite |
| Backend    | Java 21, Spring Boot    |
| Database   | PostgreSQL              |
| Container  | Docker, Docker Compose  |
| Web Server | Nginx                   |
| Server     | Ubuntu VM               |
| CI/CD      | GitHub Actions          |

### 개발 과정

```
프로젝트 환경 구축
        ↓
PostgreSQL 구축
        ↓
Spring Boot REST API
        ↓
React 구현 및 API 연동
        ↓
Docker Compose
        ↓
Ubuntu VM 배포
        ↓
GitHub Actions CI/CD
```

현재는 프로젝트 환경 구축과 PostgreSQL의 CRUD 및 데이터 영속성 검증을 완료했고, Spring Boot REST API를 구현하고 있다.

최종 목표는 실제 사용자가 웹 브라우저로 접근할 수 있는 서비스를 배포하고, GitHub에 코드를 push하면 테스트와 빌드, 배포가 자동으로 이어지는 환경을 구축하는 것이다.

이번 프로젝트에서는 기능 구현뿐 아니라 각 기술이 어떤 역할을 하는지 이해하는 데 집중하려고 한다.

- Controller, Service, Repository는 왜 분리하는가?
- 서버와 데이터베이스는 어떻게 연결되는가?
- Docker와 Docker Compose는 왜 필요한가?
- Nginx는 어떤 역할을 하는가?
- 작성한 코드는 실제 서버에 어떻게 배포되는가?
- GitHub Actions는 배포 과정을 어떻게 자동화하는가?

지금까지 개별적으로 접했던 기술들을 하나의 서비스 안에서 연결해보려 한다.

---

## AI를 사용하되, 직접 구현하기

이번 프로젝트에서는 AI를 사용하는 방식도 정했다.

**내가 먼저 설계하고 구현한다. AI는 검토와 개선에 활용한다.**

AI에게 전체 서비스를 만들어달라고 요청하면 더 빠르게 결과물을 얻을 수 있을 것이다.

하지만 이번 프로젝트의 목적은 개발 속도가 아니라 직접 구현할 수 있는 역량을 확보하는 것이다.

그래서 TDD(Test-Driven Development) 방식도 적용해보려고 한다.

```
요구사항 정의
      ↓
실패하는 테스트 작성
      ↓
최소한의 코드 구현
      ↓
테스트 통과
      ↓
리팩터링
```

AI는 테스트 케이스의 누락 여부를 검토하거나, 코드의 개선점을 찾거나, 이해하지 못한 개념을 설명받는 데 활용할 계획이다.

물론 실제 업무에서는 AI를 적극적으로 활용하는 것이 더 효율적일 수 있다.

하지만 지금은 **AI 없이도 기본적인 구조를 구현할 수 있고, AI가 작성한 코드를 스스로 검증할 수 있는 개발자**가 되는 것이 우선이다.

---

## Todo List 가 의미가 있을까?


Todo List를 개발하고 배포한다고 해서 고객의 문제를 발견하거나, 제품의 성과를 측정하고 개선하는 경험까지 얻을 수 있는 것은 아니다.

Product Engineer에게는 기술 구현 능력뿐 아니라 제품과 비즈니스에 대한 이해도 필요하다.

다만 나는 그 출발점을 풀스택 개발 역량에서 찾으려고 한다.

내가 생각하는 성장 방향은 다음과 같다.

```
Frontend Developer
        ↓
Full-Stack 역량 확보
        ↓
E2E 개발 및 운영 경험
        ↓
제품 문제 정의 및 개선
        ↓
Product Engineer
```

이것이 모든 개발자에게 적용되는 정답은 아닐 것이다.

하지만 내가 지향하는 개발자는 프론트엔드를 가장 잘하면서도, 필요하다면 서버를 수정하고 데이터베이스를 설계하고 배포까지 직접 할 수 있는 개발자다.

그 역량을 기반으로 궁극적으로는 **기능 구현이 아니라 제품이 해결한 문제를 기준으로 일하는 개발자**가 되고 싶다.

---

## 마무리

Product Engineer라는 직무를 알게 되면서 개발자로서의 성장 방향을 다시 생각하게 되었다.

프론트엔드, 백엔드, 인프라 각각의 깊은 전문성은 앞으로도 중요할 것이다.

하지만 AI의 발전으로 개발자가 접근할 수 있는 기술 영역이 넓어지고 있는 것도 사실이다.

나는 이 변화에 맞춰 프론트엔드에만 머무르기보다, 서비스 전체를 구현할 수 있는 풀스택 역량을 갖추려고 한다.

그 첫 번째 시도가 Todo List E2E 프로젝트다.

이번 프로젝트를 통해 두 가지를 확인하고 싶다.

**첫째, 나는 서비스를 처음부터 끝까지 직접 구현하고 배포할 수 있는가?**

**둘째, AI를 활용하면서도 서비스의 구조와 코드를 스스로 이해하고 통제할 수 있는가?**

이 두 가지에 답할 수 있게 된다면, 내가 생각하는 Product Engineer에 한 걸음 더 가까워질 수 있을 것이다.
